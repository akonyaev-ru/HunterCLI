# Контракт проекта — Hunter CLI

- **Проект:** `Hunter CLI`
- **Версия контракта:** `0.2`
- **Статус:** `DRAFT`
- **Последняя правка:** 2026-08-28
- **Объём этого контракта:** две функции — «Приглашение сразу» и «Уборка мёртвых
  откликов». Существующее поведение (поднятие резюме, вкладки аккаунтов,
  статистика) контрактом не описывается и не меняется.

> Шаблон рассчитан на веб-приложение. Hunter CLI — десктопная утилита без БД и
> без собственного API, поэтому §4 описывает схему состояния в файлах, а §5 —
> потребляемый контракт api.hh.ru. Разделы про фронтенд опущены осознанно.

## 1. PRD — требования

### 1.1 Цель и пользователи
Соискатель держит Hunter CLI открытым весь рабочий день ради поднятия резюме.
Программа знает о приглашениях и откликах больше, чем показывает: приглашение
обнаруживается с задержкой до суток, а список откликов копится годами (355 штук
с 2023 года) и не разбирается. Обе функции превращают уже получаемые данные в
своевременное действие.

### 1.2 Фичи по приоритету

| # | Фича | Приоритет |
|---|------|-----------|
| A | Приглашение замечается в течение одной синхронизации и показывается в журнале и в заголовке окна | P0 |
| B | Мёртвые отклики скрываются автоматически в фоне | P0 |

### 1.3 User Stories

- Как соискатель, я хочу узнавать о приглашении **в день его прихода**, а не на
  следующий день, чтобы ответить работодателю первым.
- Как соискатель, я хочу видеть приглашение **в панели задач**, потому что окно
  программы почти всегда свёрнуто.
- Как соискатель, я хочу, чтобы список моих откликов не копил годами отказы и
  висяки, и чтобы программа чистила его **сама, без моего участия**.
- Как соискатель, я хочу **знать постфактум**, что именно программа убрала.

### 1.4 Критерии приёмки

**Фича A — приглашение сразу**

- [x] AC-1: Рост числа приглашений обнаруживается на ближайшей синхронизации
      после их появления, без ожидания суточного пересчёта.
- [x] AC-2: Обнаружение стоит **один запрос** на синхронизацию
      (`/negotiations?status=active`). Счётчики `/me` не понадобились вовсе:
      приглашения живут только в `active`, а там три десятка записей — одна
      страница. Тот же запрос отдаёт кандидатов на уборку, то есть обслуживает
      обе функции сразу.
- [x] AC-3: Полный перебор всех обращений (4 запроса) остаётся суточным и
      только для статистики — новые функции его не трогают.
- [x] AC-4: При росте числа приглашений в журнал пишется запись уровня `OK`
      с числом новых приглашений.
- [x] AC-5: Заголовок окна показывает приглашение **перед** названием программы
      (решение 20) и вытесняет обратный отсчёт.
- [x] AC-6: Приглашение уходит из заголовка, когда непрочитанное прочитано на
      hh.ru, либо по истечении срока удержания (§1.6). Запись в журнале остаётся.
- [x] AC-7: Новых горячих клавиш не появляется (решение 25: раздел «Горячие
      клавиши» в справке удлинять нельзя — он вытеснит уведомление о лицензии).
- [x] AC-8: Рост непрочитанного **без** роста приглашений (пришёл отказ или
      сообщение) уведомления о приглашении не вызывает.
- [x] AC-9: При нескольких аккаунтах уведомление привязано к своему аккаунту;
      заголовок показывает открытую вкладку (решение 19).

**Фича B — уборка мёртвых откликов**

- [x] AC-10: Мёртвым считается отклик в состоянии `discard` (отказ) **или** в
      состоянии `response` без изменений дольше срока из §1.6.
- [x] AC-11: Приглашения (`invitation`) не скрываются никогда, ни при каких
      настройках.
- [x] AC-12: Уборка идёт в фоне, без подтверждения (решение владельца
      2026-08-28), не чаще раза в сутки — вместе с пересчётом обращений.
- [x] AC-13: За один проход скрывается не больше `CLEANUP_MAX_PER_RUN` штук
      (§1.6). Остаток уходит на следующие сутки.
- [x] AC-14: Каждое скрытие пишется в журнал отдельной строкой: работодатель,
      вакансия, причина (отказ / без ответа N дней).
- [x] AC-15: Ошибка скрытия одного отклика не прерывает проход и не роняет
      поднятие резюме — она пишется в журнал и проход продолжается.
- [x] AC-16: Если API отвергает скрытие как таковое (метод или коллекция не те),
      программа пишет об этом один раз и **прекращает** попытки до перезапуска,
      а не долбит в цикле.
- [x] AC-17: Функцию можно выключить в конфиге, не пересобирая программу.

### 1.5 Non-goals

- Автоотклики на вакансии, аналитика зарплат и навыков — отдельный разговор.
- Автоответы работодателям и клонирование резюме — отклонены (журнал 2026-08-28).
- Возврат скрытого отклика: API такой операции не даёт, скрытие считаем
  необратимым.
- Системные уведомления Windows и звук: владелец выбрал журнал и заголовок окна.
- Отметка приглашений прочитанными из программы — читаются на hh.ru.

### 1.6 Ограничения и назначенные значения

| Параметр | Значение | Откуда |
|---|---|---|
| Срок «без ответа» | **30 дней** | назначено агентом, владелец срок не называл; выносится в конфиг |
| `CLEANUP_MAX_PER_RUN` | **25** | страховка: ошибка в критерии не выносит весь список за один раз |
| Удержание приглашения в заголовке | **до прочтения на hh.ru** | не понадобилось изобретать: сервис сам отдаёт `read`, программа лишь показывает непрочитанное |
| Периодичность уборки | раз в сутки, на общем расписании с `needs_talks` | перебор обращений стоит 4 запроса, чаще — неприлично (факт 22–23) |

Платформа, язык, оформление интерфейса и правила выпуска — как в проекте,
изменений не вносится.

## 4. Схема состояния (вместо БД)

`config.json` — три поля в существующем разделе `settings`:

```jsonc
"cleanup_enabled": true,     // AC-17
"cleanup_stale_days": 30,    // §1.6
"cleanup_max_per_run": 25    // §1.6
```

`stats.json` — на аккаунт, рядом с существующими суточными срезами:

```jsonc
"cleanup": {"2026-08-28": 10},  // суточная отметка: уборка была, скрыто столько
"hidden_total": 10              // сколько скрыто за всё время
```

Счётчиков приглашений в файлах нет намеренно: «непрочитанное приглашение»
отдаёт сам сервис полем `read`, и хранить своё представление о нём — значит
однажды разойтись с ним. Заголовок гаснет, когда приглашение прочитано на
hh.ru; удержание по времени (Q-2) поэтому не понадобилось.

Оба файла проходят существующие миграции схемы; отсутствие полей означает
первый запуск и трактуется как «уведомлять не о чем, уборку начинать с нуля».

## 5. Потребляемый контракт api.hh.ru

> Проверено 2026-08-28 без токена. Публичная спецификация hh соискателя не
> описывает (факт 26), поэтому контракт снят пробами и фиксируется здесь.

| Операция | Метод и путь | Статус проверки |
|---|---|---|
| Активные обращения | `GET /negotiations?status=active&per_page=100` | **проверено живым запросом** |
| Полный перебор (статистика) | `GET /negotiations?per_page&page` | используется сегодня |
| **Скрыть обращение** | **`DELETE /negotiations/active/{nid}`** | метод подтверждён пробой; **живым запросом НЕ проверен** |

Отброшено: `GET /me` → `counters` (форма подтверждена — `new_resume_views`,
`unread_negotiations`, `resumes_count`, — но не нужна, см. AC-2).

### 5.1 Что показала разведка 2026-08-28 (все неизвестные закрыты)

| # | Было | Стало |
|---|------|-------|
| U-1 | поля даты неизвестны | есть `created_at` и `updated_at` (ISO со смещением `+0300`), плюс `read`, `has_updates`, `hidden`, `decline_allowed` |
| U-2 | попадают ли отказы в `active` | **да**: в `active` лежат и `response`, и `discard`, и `invitation` |
| U-3 | форма `counters` | подтверждена, но не понадобилась |

**Главное открытие, меняющее объём функции B.** Коллекция `active` — это не
«все обращения», а рабочий список: 32 записи из 356 на первом аккаунте и 24 на
втором. Остальное сервис увёл в архив сам. Скрытие работает **только** по
`active` — DELETE принимается для неё одной, все прочие имена коллекций дают
405. Значит уборка касается рабочего списка, а не архива:

| | аккаунт 1 | аккаунт 2 |
|---|---|---|
| всего обращений | 356 | — |
| в `active` | 32 | 24 |
| отказов под уборку | 9 | 6 |
| висяков старше 30 дней | 1 | 0 |
| **итого к уборке** | **10** | **6** |

Срок «30 дней» почти не работает: сервис уводит старое из `active` раньше. Всю
работу делает критерий «отказ». Правило оставлено — оно верное и пригодится,
когда список подрастёт.

### 5.2 Что осталось непроверенным

`DELETE /negotiations/active/{nid}` **ни разу не выполнялся против настоящего
hh.ru**. Проверен фейковым сервером в тестах и пробой метода без токена
(403 против 405). Разрешения на запись в аккаунт владельца не было.
